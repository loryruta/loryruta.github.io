BrickFormer

Website Github

A tool to convert 3D models into LEGO constructions.
BrickFormer was a toy project, it is the result of my passion for Computer Graphics, GPU Computing and LEGO's.
After I had the idea, I was deeply challenged by the complexity of the problem, and my hobby during university time became trying to find a method to solve it.

User pipeline

Upload the model

The user uploads a 3D model (picked for example from Sketchfab). The supported input formats are .gltf and .glb.
These are general purpose formats to which any other can typically convert to.

User pipeline

Choose the model orientation

The model orientation can be any, depending on the tool that was used to craft the model. Hence why we provide a functionality to define the up axis and to flip axes.

User pipeline

Choose the grid resolution

The grid resolution defines how many bricks are used in the XZ dimensions (+Y up). The height (i.e. the number of slices) will be proportional to the model size.

User pipeline

Choose the colors to use

We support all common LEGO brick colors available on the market. Via UI, it is possible to exclude colors that must not be used during the conversion, hence defining a custom palette.

Problem statement

The problem that BrickFormer aims to solve, is to maximize the similarity between a LEGO construction $\mathcal{p}$ and a target 3D model $\mathcal{M}$. The similarity is defined in terms of shape and color. The "LEGO construction" has a given resolution and is a combination of bricks drawn from a provided discrete set. Among the possible combinations some of them are not valid.
\[\begin{aligned} p^* = \arg\max_{p \in \mathbb{P}} \operatorname{similarity}(p, \mathcal{M}) \end{aligned} \]

Problem statement

The similarity function

We can trivially model a similarity score that will be higher if $p$ is close to the target model. Considering both live in the same 3D space, a measure of similarity could be provided by aggregating the structural distance, and color distance, of every individual brick $b$ to the closest point on the model.
\[\begin{aligned} \operatorname{similarity}(p, \mathcal{M}) = \dfrac{1}{|p|} \sum_{b \in p} \left( \operatorname{dist}(b_{\text{position}}, \mathcal{M}) + \operatorname{dist}(b_{\text{color}}, \mathcal{M}) \right) \end{aligned} \]
The closest point on the model could be efficiently retrieved through a spatial data structure (e.g. a KD-tree).

Problem statement

The solution space

To simplify the problem, the set of available bricks $\mathbb{B}$ is made of standard LEGO bricks (as shown below). Different rotations of these bricks are treated as different bricks. Placements locations are binned in voxels within a 3D grid defined by the input resolution $\mathcal{R}$. Nonetheless these simplifications, the solution space $\mathbb{P}$ remains discrete and insanely large. For every voxel, any combination of bricks could be placed, and of any color. The cardinality would be:

\[\begin{aligned} |\mathbb{P}| = \left| \mathcal{R}_x \times \mathcal{R}_y \times \mathcal{R}_z \times \mathbb{B} \times \mathbb{C} \right| \end{aligned} \]

Where $\mathbb{C}$ is the set of available colors.

Most notably, the solution space is populated with invalid constructions. For example: overlapping bricks, floating bricks, bricks spanning out of the provided resolution. Moreover, some constructions might share high similarity, but one should be preferred to another in terms of stability.

It's clear that addressing the problem globally is unfeasible, hence why I've opted for a greedy solution.

The greedy algorithm

Bottom-up, slice-by-slice construction

In real life, LEGO constructions are built bottom-up, hence I decided having the tool doing the same.

The model is first sliced into $\mathcal{R}_y$ slices, and each slice is processed incrementally. In this way we can strip the height dimension from the search space:
\[\begin{aligned} | \hat{\mathbb{P}} | = \left| \mathcal{R}_x \times \mathcal{R}_z \times \mathbb{B} \times \mathbb{C} \right| \end{aligned} \]
Putting in practical numbers, the number of available bricks is $|\mathbb{B}| = 22$, and the colors are $|\mathbb{C}| = 67$. If we constrain the resolution $\mathcal{R}_{\{x,z\}}$ to $\{1, ..., 150\}$, the worst case solution space would be: \[\begin{aligned} 150 \times 150 \times 22 \times 67 = 33165000 \end{aligned} \] For each, we evaluate the similarity function, leading to a final algorithm that would be already treatable by modern GPUs (possibly chunked in multiple kernel dispatches).

However, we still didn't get rid of invalid solutions: some solutions could have overlapping bricks, floating bricks or bricks spanning out of the conversion grid. While checking if a brick is floating or out of bounds is simpler in the 2D case (and could be done when evaluating the similarity function), checking if bricks of the same solution are overlapping is not trivial as it requires a second pass and additional storage.

Slicing the model

Whenever a new slice is processed for a given $y \in [0, \mathcal{R}_y[$, the model is sliced and voxelized for that $y$.

A kernel is dispatched with one invocation for every triangle. The world-space triangle is intersected against a box representing a voxel of the current slice. If the intersection test succeeds, the voxel is filled with the interpolated triangle's color.

The greedy algorithm

Placement-by-placement construction

Another insight is that LEGO constructions are built brick-by-brick and typically consecutive placements are illustrated close to each other.

This inspired me for the final algorithm: starting from a state $\mathcal{S}_i$ of the construction, all possible placements $\pi$ within the slice are evaluated. Among these, it is picked the placement $\pi^*$ which evaluates the highest to a hand-crafted placement score function $f_{\mathcal{S}_i}$. \[\begin{aligned} \pi^* = \arg\max_{\pi \in \mathbb{P}^2} f_{\mathcal{S}_i}(\pi) \end{aligned} \] Once the placement is selected, it is added to the construction: \[\begin{aligned} \mathcal{S}_{i+1} \leftarrow \mathcal{S}_i \cup \pi^* \end{aligned} \] The process is repeated within the current slice, until the best score remains above a pre-defined threshold $\tau_f$. When this condition is false, it restarts for the next slice until the full height of the construction ($\mathcal{R}_y$) is reached.

The greedy algorithm

Placement score function

The score function was designed empirically.
After several experiments with different measures, I ended up with: \[\begin{aligned} h_n = 1 - \dfrac{h}{3 \cdot 255} \end{aligned} \] \[\begin{aligned} f_{\mathcal{S}_i}(\pi) = \dfrac{b}{B} \cdot \left( \dfrac{d}{b} + \operatorname{sigmoid}( 32 \cdot (h_n - 0.130) ) \right) + (0.8 \cdot \dfrac{c}{b} + 0.2) \end{aligned} \] Where:
  • $b$ is the size of the brick.
  • $B$ is the maximum brick size.
  • $d$ is the number of different placements on the previous slice that this placement connects.
  • $h$ is the Manhattan RGB distance between the brick and the model.
  • $c$ is the number of voxels filled by the model's slice, that this placement covers.

As it can be deduced from the above, each variable encodes a local similarity and stability:
  • $b$: the larger the brick, the better. This improves stability.
  • $d$: the more diverse placements are connected on the previous slice, the more stable it is. For example, avoids making same brick piles.
  • $h$: addresses color similarity.
  • $c$: addresses structural similarity.

Placement Solver implementation

As mentioned, to compute the next placement, the whole solution space is explored. In the actual implementation, the color is assigned later.

I've used the global warp ID instead of the global invocation ID, the reason is the latter would neglect warp intrinsics that are useful when having to iterate all cells covered by the placement.

The global warp ID is expanded into a 3-dimensional coordinate: the XZ of the placement and the brick ID (the type of brick).

__device__ bool is_outside_or_overlapping(placement, current_placements)
{
    __shared__ int result[32];

    int warp_idx = threadIdx.x >> 5;
    if (IS_FIRST_WARP) result[warp_idx] = false;
    __syncwarp();

    const auto& brick = bricks[placement.bid]; // float[16][16]
    // Iterate the cells covered by the brick in parallel
    iterate_brick_grid([&](int bx, int by) {
        if (brick[by][bx]) {
            int mx = placement.x + bx;
            int my = placement.z + by;

            bool out_of_bounds = mx < 0 || mx >= RESOLUTION_X || my < 0 || my >= RESOLUTION_Y;
            bool overlapping = current_placements.read_pixel(mx, my).x != NO_PLACEMENT_VALUE;
            if (out_of_bounds || overlapping) atomicOr_block(&result[warp_idx], true);
        }
    });
    __syncwarp();

    return result[warp_idx];
}

Placement Solver implementation

Several measures for the placement are evaluated and aggregated into a final score.

Other heuristics are taken:
  • "hole filling" placements are prioritized to avoid, for example, gaps in a flat surface
  • Degeneration of the shape is avoided by not selecting placements that don't intersect the model enough

    float b = eval_brick_size(placement.brick_id);
    float c = eval_colormap_coverage(placement, voxelized_model_slice);
    float d = eval_connected_bricks(placement, prev_slice);
    float h = eval_colormap_rgb_distance(placement, voxelized_model_slice);

    float bn = float(b) / float(BRICK_MAX_EXTENT_X * BRICK_MAX_EXTENT_Z);
    float cn = float(c) / float(b);
    float dn = float(d) / float(b);
    float hn = std::max(h, 0);
    hn = sigmoid(16.0f * 2.0f * (hn - 0.13071895f)) / (3.0f * 255.0f); // Empirical
    hn = 1.0f - hn;

    // If the placement doesn't intersect any model's voxel,
    // it is only allowed to fill holes!
    if (c == 0) {
        return is_filling_hole(placement) ? bn : -INFINITY;
    }

    // If the placement doesn't cover enough model's voxels, it is discarded
    if (cn < 0.2f) return -INFINITY;

    // Final score
    return bn * (dn + hn) + (0.8f * cn + 0.2f);

LEGO Renderer

A simple renderer of the LEGO model, wouldn't show a clear distinction of the bricks (Figure 1)

It was fundamental to draw a border around different placements and around the studs, to aid understanding of the brick size. The way I solved this issue is through deferred rendering. The scene is first drawn into a gbuffer which hosts:
  • the placement color
  • the depth map
  • the outline guide
The outline guide is what is used to generate the outline.

It is an integer number, that is different for every placement, and is different between the studs on top of the placement. When the gbuffer is ultimately drawn to screen, a convolution operation is performed: if at least one pixel within the kernel has a different outline guide, the central pixel is the outline and is set to be black.

App architecture

The app launches 2 threads, the main thread that is used for visualization (OpenGL 4.6); and the sync thread that ensures the local software version matches the latest version, and checks the validity of the Firebase authentication token.

Don't get inspiration from this to authenticate users in your application.

When the conversion starts, a conversion thread is launched. This thread fires events to the main thread while the conversion is in progress. An example of an event is slice completion, this will trigger the generation of brick vertices, that are baked to a GPU vertex buffers, to progress the visualization of the LEGO construction.
